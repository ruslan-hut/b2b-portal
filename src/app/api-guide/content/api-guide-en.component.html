01Turn access on

API access is switched on by your account manager — it is off by default. Tell your manager you are planning an integration and they will open the API for your account.

Then sign in to the portal as usual and open Profile. The API access section sits at the bottom of the page; once access is on, a New key button appears in it.

Who does what. Your manager opens access once. Creating, rotating and revoking keys is yours to do — you never have to ask us for that.

02Issue a key

Click New key and fill in the form:

Scopes

Give a key only what that particular integration needs.

ScopeGrants
catalog:readcatalog, product detail, order pricing (quote)
orders:readorder list and detail, statuses, invoices, tracking
orders:writeplacing orders
profile:readprofile and delivery addresses
profile:writeediting the profile and addresses

The key is shown once

A key looks like cmx_<mode>_<prefix>_<secret>. The mode is live or test. The 8-character prefix is public: it identifies the key in your list and in our logs, and it is what to quote in a support request. The secret is never stored in the clear and cannot be recovered.

Start with a test key. Tick “Test mode” — such a key reads normally, and POST /orders runs the full validation and pricing but saves nothing. Once the integration works, create a separate live key.

03Your first request

The simplest check is GET /me. It needs no scope and tells you straight away whether the key is alive and what it is allowed to do.

GET/me · curl
curl -s {{ base }}/me \
  -H "Authorization: Bearer cmx_test_Ab3dEf9h_…"

The X-API-Key header works just as well as Authorization.

200 OKresponse (trimmed)
{
  "success": true,
  "data": {
    "client": { "uid": "c-1f4a…", "name": "Azhur Studio" },
    "currency": { "code": "UAH" },
    "vat_rate": 20,
    "addresses": [ { "uid": "a-88c1…", "is_default": true, "city": "Kyiv" } ],
    "api_key": {
      "name": "Our ERP",
      "scopes": ["catalog:read", "orders:read"],
      "is_test": true,
      "expires_at": "2027-08-17T10:00:00Z",
      "rate_limit_read_per_minute": 600,
      "rate_limit_write_per_minute": 60
    }
  },
  "request_id": "req_9f2c…"
}

Every response uses the same envelope: success, then data or error, plus request_id. The same id comes back in the X-Request-ID header — log it on your side and we can find any request of yours in seconds.

Got a 401? One answer covers every cause — unknown key, revoked, expired, or access switched off. Check that you copied the key in full, that it is not revoked in your profile, and that your manager has enabled access. After repeated failures (20 in 10 minutes) your IP is blocked for a while — wait out the Retry-After header.

04Catalog and prices

The catalog already comes scoped to you: only products priced for your price list and sellable in your country. Prices are integer cents.

GET/catalog/products
curl -s "{{ base }}/catalog/products?limit=2&search=gel" \
  -H "Authorization: Bearer $COMEX_KEY"
200 OKarray of products
{
  "success": true,
  "data": [
    {
      "uid": "p-7b21…",
      "sku": "DBR-1042",
      "barcode": "4820001234567",
      "name": "Gel Polish 8 ml, shade 042",
      "base_price": 18000,          // 180.00 before discount and VAT
      "price_with_discount": 16200,
      "price_final": 19440,         // with discount and VAT
      "vat_rate": 20,
      "discount_percent": 10,
      "available": true
    }
  ]
}
FieldMeaning
base_pricebefore discount, without VAT
price_with_discountwith your discount, without VAT
price_finalwith discount and VAT — what you actually pay per unit
availabletrue when the store holds stock for you

Stock levels are never exposed — only the available flag. If the quantity you need is short, you find out when the order is priced.

Matching your own SKUs

Instead of pulling the whole catalog, send your SKUs or barcodes: you get priced products back plus a separate not_found list.

POST/catalog/products/lookup
curl -s {{ base }}/catalog/products/lookup \
  -H "Authorization: Bearer $COMEX_KEY" \
  -H "Content-Type: application/json" \
  -d '{"skus":["DBR-1042","DBR-9999"],"language":"en"}'

Also available: /catalog/categories, /catalog/languages, a product by uid or by SKU (/catalog/products/by-sku/{sku}) and its images.

05Orders

Price first, then place. The request body is identical for both, so going from a dry run to a real order is a one-line change of URL.

POST/orders/quote · stores nothing
curl -s {{ base }}/orders/quote \
  -H "Authorization: Bearer $COMEX_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "items": [
          {"product_uid": "p-7b21…", "quantity": 6},
          {"product_uid": "p-3c08…", "quantity": 2}
        ],
        "client_reference": "PO-2026-118",
        "comment": "Ship together with the previous order"
      }'
200 OKquote
{
  "success": true,
  "data": {
    "quote": true,
    "items": [ { "product_sku": "DBR-1042", "quantity": 6, "total": 116640 } ],
    "subtotal": 129600,
    "total_vat": 25920,
    "delivery_cost": 0,
    "total": 155520,
    "currency_code": "UAH"
  }
}

The money reconciles as total = subtotal + total_vat + delivery_cost (shipping sits in neither subtotal nor total_vat).

Placing the order

The same request against POST /orders creates a confirmed order: it lands in your manager's queue immediately. Always send an Idempotency-Key — with it, a retry after a dropped connection can never create a second order.

POST/orders · needs orders:write
curl -s {{ base }}/orders \
  -H "Authorization: Bearer $COMEX_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: PO-2026-118" \
  -d '{"items":[{"product_uid":"p-7b21…","quantity":6}],
       "client_reference":"PO-2026-118"}'
  • 201 — order created; the response carries uid and number.
  • 200 with "test": true — a test key: validated and priced, nothing saved.
  • 409 — the same Idempotency-Key sent with a different body.
  • A retry with the same key and the same body within 24 hours replays the original response with Idempotent-Replayed: true.

The delivery address defaults to your default one unless you pass shipping_address_uid. client_reference is your own number (a PO): it is stored, shown to staff and searchable.

When an order is rejected

400rejection
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Order rejected",
    "details": { "reason": "insufficient_stock" },
    "extra": { "problems": [ { "product_uid": "p-3c08…", "reason": "insufficient_stock" } ] }
  }
}

Common values of details.reason: validation (per-line problems in extra.problems), insufficient_stock, address_invalid, business_registration_required.

Following an order

RequestReturns
GET /orders?updated_since=…everything changed since your last sync

The phase field is one of placed, confirmed, processing, shipped, delivered, cancelled. For routine syncing use updated_since — far cheaper than re-reading the whole list.

06Code: Python and Node

Pythonrequests
import os, requests

BASE = "{{ base }}"
S = requests.Session()
S.headers.update({"Authorization": f"Bearer {os.environ['COMEX_KEY']}"})

# 1. check the key
me = S.get(f"{BASE}/me", timeout=15).json()["data"]
print(me["client"]["name"], me["api_key"]["scopes"])

# 2. resolve a product by your own SKU
found = S.post(f"{BASE}/catalog/products/lookup",
               json={"skus": ["DBR-1042"]}, timeout=15).json()["data"]
product = found["products"][0]

# 3. place the order (safe to retry thanks to Idempotency-Key)
r = S.post(f"{BASE}/orders",
           headers={"Idempotency-Key": "PO-2026-118"},
           json={"items": [{"product_uid": product["uid"], "quantity": 6}],
                 "client_reference": "PO-2026-118"}, timeout=30)

body = r.json()
if not body["success"]:
    raise RuntimeError(body["error"]["message"], r.headers.get("X-Request-ID"))
print("order", body["data"]["number"], body["data"]["total"] / 100)
Node.jsfetch (18+)
const BASE = "{{ base }}";

async function call(path, init = {}) {
  const res = await fetch(BASE + path, {
    ...init,
    headers: {
      Authorization: `Bearer ${process.env.COMEX_KEY}`,
      "Content-Type": "application/json",
      ...init.headers,
    },
  });
  const body = await res.json();
  if (!body.success) {
    // log request_id — it is how we find the request
    throw new Error(`${body.error.code}: ${body.error.message}`);
  }
  return body.data;
}

const quote = await call("/orders/quote", {
  method: "POST",
  body: JSON.stringify({ items: [{ product_uid: "p-7b21…", quantity: 6 }] }),
});
console.log("to pay:", quote.total / 100, quote.currency_code);

07Errors and limits

HTTPerror.codeWhat to do
400VALIDATION_ERRORfix the request body; details in error.fields or extra.problems
401UNAUTHORIZEDkey invalid, revoked, expired, or access switched off
403FORBIDDENmissing scope (see details.required_scope) or a write with a test key
404NOT_FOUNDno such object — or it is not yours
409CONFLICTsame Idempotency-Key, different body
429RATE_LIMIT_EXCEEDEDwait Retry-After seconds and retry
503MAINTENANCEplanned maintenance — retry later

Rate limits

Two limits per key: 600 reads and 60 writes per minute. Every response carries X-RateLimit-Limit and X-RateLimit-Remaining; a refusal adds Retry-After and X-RateLimit-Reset.

  • Request body up to 1 MiB, request timeout 10 seconds.
  • Lists are paged with offset and limit (max 100).
  • Retry with backoff on 429 and 5xx; retrying a 4xx will not help.

08Keeping keys safe

  • A key is access to your prices and your orders. Keep it in environment variables or a secret store — never in code or in a repository.
  • Never use a key from a browser or a mobile app — server-side only.
  • One key per system: revoking one then never stops the others.
  • Keys are valid for 365 days. Watch the expiry date in your profile.

Rotate issues a new key and keeps the old one working for a short grace period — 24 hours. That is the no-downtime way to refresh: create the new key, update your configuration, let the traffic move over.

Revoke is immediate and final: anything using that key stops working at once. That is exactly what to do if you suspect a key has leaked.
